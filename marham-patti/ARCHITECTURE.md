## 1. Overview

**Marham Patti** is an AI-powered, **multi-tenant, white-label, vertical-configurable** healthcare operating system for Pakistan — clinics (OPD), laboratories, pharmacies, and home-healthcare. One platform unifies a patient/customer record across clinic, lab, pharmacy, home sample collection, billing, accounting, patient & doctor apps, an own online pharmacy, and an assist-only AI suite — and is **sold per vertical** (Pharmacy / Lab / Clinic / Clinic+Pharmacy / Full) with **sub-feature-level control per tenant**.

- **Product:** Marham Patti (the app). **Built & delivered by:** AboveNext. **First tenant:** Ganatra Clinic (Full suite).
- **Tenancy:** Multi-tenant from day one; isolation enforced by Postgres RLS. Branch-aware within a tenant.
- **SaaS model:** every capability is a **feature flag**; flags are bundled into **vertical presets**; each tenant starts from a preset and is **fine-tuned per tenant** (overrides). White-label-ready (theme/identity/sender hooks built into the foundation).
- **Core job-to-be-done:** give a non-technical owner **total, accountable control** (every rupee and every strip of medicine traceable to a person and a time) while letting **inexperienced staff perform like experts** via assist-only AI — across whichever vertical they bought.

## 2. Principles (non-negotiable, every step)

1. **AI is assist-only.** AI never independently diagnoses, prescribes, approves lab results, or sells. It drafts; a **licensed human confirms** (doctor / pharmacist / pathologist). Every AI output is a suggestion with approve/reject + audit.
2. **Accountability everywhere.** Every create/update/delete and every stock movement logs to a user, time, and reason. Sensitive reads (CNIC reveal, confidential data) are audited too.
3. **Offline-first for critical paths.** Token, vitals, POS sale, capture work offline and sync on reconnect. AI features require connectivity and **queue** until online.
4. **Paper-first reality.** Design *for* paper (one-tap tokens, print/handwrite vitals, doctor comfort levels, end-of-day photo→AI register import).
5. **Tenant isolation is sacred** and is **always-on infrastructure, never a feature flag.** `tenant_id` + RLS on every business table.
6. **Configurable per tenant (SaaS).** Every capability is a **feature flag** (sub-feature granularity). Flags bundle into **vertical presets** with per-tenant overrides. Disabled features hide in UI **and** are forbidden server-side, cleanly (no orphan routes/nav).
7. **White-label ready.** Tenant **theme tokens, app identity (name/logo/PWA/letterhead), notification sender identity, and domain resolution** are honored everywhere from the foundation, so a tenant's branding is applied at runtime across every surface.
8. **No secrets in the repo.** Only `.env.example` placeholders. ARCHITECTURE.md + PROGRESS.md are PUBLIC.
9. **Design quality + performance are requirements, not polish.** Polished shadcn/ui + tokens, light/dark, motion, animated charts, skeletons — never raw HTML. **Performance is a gate:** 90+ Lighthouse on public/patient-facing surfaces; a strict fast-&-smooth budget on internal tools (§13).
10. **"Simplicity" = ease of use for non-technical/illiterate users** (plain language, few clicks, large touch targets, icons, voice, Urdu) — NOT a basic look.
11. **Two-tier i18n — with a surface exception.** The i18n **framework is always in place**; strings resolve through it on every surface. **Language coverage is per surface:** the **vendor console is English-only** (71) and, from Phase 15, the **tenant staff app is English-only too** (owner decision — no language switcher, no RTL on tenant surfaces; English values only, the framework retained so a future language is additive, never a rebuild). Where a surface *is* bilingual, UI text → **English + Urdu** (parity gate) and AI-generated/conversational output → **English + Urdu + Roman Urdu**.
12. **Production & real data are human-gated.** Agent works on `staging`/dummy only. `main` deploys ONLY on the owner's explicit Telegram command.
13. **Specs are authoritative.** Current `specs/NN-*.md` is the source of truth; missing → `[HUMAN_REQUIRED]`.

## 3. Always-on infrastructure (never a feature flag, never sellable as optional)

Auth, **tenant isolation/RLS**, audit log, the offline core, the capability/flag engine itself, branding resolution, i18n, and the design/perf system. These are safety/integrity, not features. Every tenant gets them regardless of vertical or plan.

## 4. Feature flags, verticals & presets (the SaaS control layer)

- **Flag catalog** in `@mp/shared` — every gated capability is a string key (e.g. `pharmacy.pos`, `pharmacy.online`, `pharmacy.aiReader`, `lab.results`, `lab.homeCollection`, `clinic.consultation`, `clinic.commission`, `accounting.full`, `accounting.lite`, `patient.app`, `ai.suite`). **Sub-feature granularity** — modules expose multiple flags, not one. Synced + reconciled on boot (like the permission catalog).
- **Vertical presets** (a preset = a flag bundle):
  - **Pharmacy** — POS, inventory, purchases/suppliers, customer-lite record, `accounting.lite` (toggle to full); online-pharmacy / AI-reader / barcode-labels as flags.
  - **Lab** — test catalog, orders, samples + chain-of-custody, results/approval, branded reports, home-collection (flag), `accounting.full` (toggle to lite); patient app (flag).
  - **Clinic (OPD)** — patients, appointments/token, vitals, consultation, e-prescription, doctor commission, `accounting.full`; pharmacy/lab off.
  - **Clinic + Pharmacy** — OPD + pharmacy together, **lab off** (your friend's-style / "OPD & pharmacy" target).
  - **Full Suite** — everything (Ganatra).
- **Per-tenant overrides:** start from a preset, then flip any individual flag for that tenant (e.g. Clinic + a small pharmacy on + lab off).
- **Precedence (deliberate):** **flag first** (does the tenant have the capability) **then permission** (can this user use it). A feature absent by flag is invisible/forbidden regardless of role; a feature present by flag still respects RBAC.
- **One Patient model, flag-driven views.** Pharmacy-only tenants see a **light "customer" view** (name + phone + udhaar/credit + purchase history) via `customers.medicalRecord=off`; Clinic/Full see the full medical record. Same model — a pharmacy that later adds a clinic just lights up the medical fields (no migration).
- **Accounts is a flag with two modes:** `accounting.lite` (simple cash in/out) vs `accounting.full` (double-entry). Vertical-aware: it seeds the right chart of accounts and only wires posting consumers for **enabled** modules (a lab posts no COGS/inventory).

## 5. Tech stack

- **Monorepo:** pnpm + Turborepo. Packages: `@mp/shared`, `@mp/ui`, `@mp/db`, `@mp/config`, `@mp/ai`, `@mp/flags` (capability engine), `@mp/brand` (white-label theming/identity).
- **API:** NestJS (TypeScript), modular per domain. **No `/api` route prefix** (proxy strips it; §13/§15).
- **Web:** Next.js 15 (App Router) + React + Tailwind + shadcn/ui. PWA. **Performance-budgeted** (route code-split, streaming/RSC, image + font strategy) for 90+ on public surfaces.
- **ORM/DB:** Prisma + PostgreSQL 16 + **RLS**. `prisma generate` after install, before build, in CI **and** deploy.sh.
- **Cache/queue:** Redis (sessions, rate-limits, jobs, offline-sync coordination).
- **Search:** Postgres `pg_trgm` (patient/medicine fuzzy) at launch; Meilisearch optional later for the 20k–50k medicine catalog.
- **Files:** Cloudflare R2 (reports, images, proofs) — presigned, tenant-scoped keys.
- **AI:** provider-agnostic `@mp/ai`; per-tenant keys; per-task model routing; quality-first tiering; spend metering; budget caps. `[DECIDE AT BUILD]` default models/providers per task.
- **Notifications:** WhatsApp + SMS + in-app, provider-agnostic; **per-tenant sender identity hook**. WhatsApp provider + per-tenant verified number `[DECIDE AT BUILD]`.
- **Infra:** AboveNext Oracle Cloud ARM VPS, aaPanel, Nginx, PM2, Node v22, Cloudflare DNS. Staging + human-gated production. All tenants under `marhampatti.com` at launch; per-tenant custom-domain resolution is a built-but-dormant hook.
- **Printing:** 80mm thermal via browser-print CSS at launch; raw ESC/POS `[DECIDE AT BUILD]`. Barcode: USB keyboard-wedge; self-printed labels.

## 10. Data model (summary — full schema per spec; every business table carries `tenant_id`, most `branch_id`)

- **Tenant** 1─* **Branch**; **Tenant** 1─* **User**; **Tenant** 1─ **TenantFlags**/**BrandingProfile**/**Capabilities**.
- **Patient/Customer** (one model; phone primary, CNIC secondary) 1─* **PatientRelation**, **Appointment**, **Encounter**, **Prescription**, **LabOrder**, **Sale**, **PatientCredit** (udhaar), **ConsentRecord**, **NotificationPref**. Medical fields gated by `customers.medicalRecord`.
- **Appointment** ─ **Token**; **Encounter** ─ **Vitals**, **Diagnosis**, **Prescription**.
- **Prescription** 1─* **PrescriptionItem** (→ **Medicine**); privacy + dual-copy flags.
- **LabOrder** 1─* **LabOrderTest** (→ **LabTest**/**LabPackage**) ─ **Sample** (barcode, chain-of-custody) ─ **Result** (per **ResultTemplate**, age/gender ranges) ─ **ReportApproval**.
- **Medicine** (brand/generic, strength/form/pack) 1─* **Batch** (expiry, FEFO); **StockMovement** (every change → user+reason); **Sale** 1─* **SaleItem**; **CartHandoff**.
- **PurchaseOrder**/**GRN**/**Supplier**/**SupplierPayment**; **StockTransfer**.
- **HomeCollection** ─ **PhlebotomistAssignment** ─ **CollectionProof**.
- **Accounts:** **Account** (chart) ; **JournalEntry** 1─* **JournalLine** (double-entry) ; **FiscalPeriod**. Lite mode: **CashLedger**. Auto-posted from enabled modules only.
- **Commission**: per-doctor config → **CommissionEntry**.
- **AI:** **AiProviderConfig**, **AiTask**, **AiSuggestion**, **AiFeedback**, **AiMemory**, **AiBudget**.
- **Audit:** **AuditLog** (actor/action/entity/reason/time), RLS-scoped.

## 13. Performance budget (the "90+ where possible & best" gate)

- **Public/patient-facing** (patient PWA, online pharmacy storefront, login, any pre-auth/SEO page): **Lighthouse mobile ≥ 90** for Performance + Best-Practices + Accessibility; PWA installable. Targets: **LCP < 2.5s**, **CLS < 0.1**, **TBT < 200ms** on mid-range mobile.
- **Internal authed tools** (POS, lab, consultation, accounts, dashboards): "fast & smooth" — interaction-ready quickly, no jank; route-level **JS budget** enforced; virtualized long lists; skeletons/streaming. Lighthouse SEO not chased behind auth.
- **How:** Next.js RSC/streaming, route code-splitting, dynamic import of heavy widgets (charts/editors), image optimization (R2 + next/image), **Urdu/Nastaliq font strategy** (subset + `font-display: swap` + system fallback so Urdu never tanks LCP), defer non-critical JS, cache static assets. CI runs Lighthouse on the public routes and fails the gate below budget.

231. `231-production-boot-write-policy` — authored the day production went live, to encode a rule the cutover exposed: **a deploy ships code and must not change data.** Several `onApplicationBootstrap` hooks wrote to the database on every start — harmless on staging (a fresh environment each deploy) and wrong on a live system holding a real tenant's records. All four boot writes are insert-if-absent (verified: none ever updates or deletes an existing row, so no operational data was ever at risk), and the spec classifies each rather than blanket-gating: the **permissions and flags catalogs stay** — they insert only the system-definition keys the newly-shipped code declares, and gating them off production would ship a feature whose permission or flag is missing from the DB, broken and hard to trace — while the **subscription-package reconcile becomes seed-once**: it inserts the starter packages only into a genuinely empty catalogue, so a package the operator deletes in the vendor console stays deleted instead of returning on the next boot (the per-key absent check being exactly what resurrected it). The baseline Ganatra seed was already gated off production in the cutover fix; the vendor-owner bootstrap is already env-gated and merely gains a documented lifecycle. A single shared `isProductionBoot()` guard routes the existing seed gate and stands as the one mechanism any future boot hook creating operational data must use, so the rule is enforced rather than remembered. The guarantee stated exactly: after this, a production deploy changes code and — only when the new code requires it — **adds** a system-definition key it declares; it never creates, edits or deletes a tenant, user, sale, customer or managed package, and data changes on production happen only through the application's own actions. No schema change, no migration, no change to any existing row.

233. `233-invite-security-and-pwa-asset-fixes` — the round's headline is a **security defect**: the owner deliberately truncated the `token` in a staff invite URL and the page still let him set a password, meaning the token was not matched whole. Since that token is the only thing between a link and control of a Tenant Owner account, a sufficient prefix collapses the search space and makes an account guessable — so it is built first and ships even if nothing else in the spec does. The spec forbids inferring the cause: log the received token, its length and the **lookup actually performed** (`startsWith`, a `LIKE` wildcard, a column too short to hold the issued value, or a validation that checks a token's *presence* while loading the invite by user), name it in one sentence in PROGRESS-HISTORY, and only then fix. Required after: whole-value **constant-time** comparison against a digest, single-use consumption **in the same transaction as the password write** so a concurrent second use cannot also succeed, and consumed/expired/unknown all returning the **same** non-enumerating outcome (143's rule — the difference is itself information). 234. `234-payment-allocation-and-app-icon` — the counter's payment model outgrew "this sale or change". Three real situations the owner hit: a customer owing Rs 3,000 buys Rs 2,000 and hands over Rs 17,000 expecting the old balance cleared and the rest held; the same customer wanting Rs 300 against old credit and Rs 500 back; and plain overpayment kept as advance. The recommitted mockups answer it with the **`.alloc` block** — money allocated across four destinations, **This sale → Old credit → Change due → To advance**, filled in that order with the remainder split between the last two and each amount editable, a zero row **dimmed rather than hidden** so the cashier can still direct money into it, and **Confirm blocked while received and allocated disagree**, because money that does not add up must never commit. The architectural care is in what it does *not* do: an amount sent to **Old credit is a customer payment against the ledger**, identical to the Customers screen's Record payment, and **advance is 227's negative balance** — neither is an extra tender leg, so `splitPaymentSummary` and the exact-sum rule stay byte-identical and a sale's recorded payment can never exceed its own total, which would corrupt day-close and every report. Day-close instead sees the sale's own split unchanged plus the collection alongside it, so the drawer still reconciles against all cash taken. Format is **one row per line item** grouped by invoice number (a distributor's own export looks that way, and forcing invoice-per-row would make the tenant restructure the file that column mapping exists to avoid), with conflicting header values across one invoice's rows reported as an **error rather than guessed**. The rule that makes the two paths incapable of diverging: **the import calls the same service the entry screen calls** rather than writing rows itself. One transaction per invoice so a failure never leaves an invoice missing half its lines; **idempotent on invoice number**, a re-import skipping what already exists rather than duplicating or updating (a purchase is never edited — see 261); and it **never auto-creates a product or a supplier**, since inventing a half-specified product from a purchase row would poison the catalogue. The acceptance is that imported stock **sells correctly at POS**, not that a row count matched.
267. `267-offline-recovery-and-round-fixes` — the error family's fifth round, narrowed to a specification because the owner supplied both screenshots and the behaviour he wants. The two near-identical offline screens are **two implementations** — the pattern again — so one is kept, the other deleted, and the "Changes saved locally" chip that distinguished them becomes a conditional element on the survivor, shown only when the queue actually holds something. Retry's behaviour is adopted verbatim from the owner: **still offline → a toast, and stay put**; **back online → reload the data over AJAX and return to the page the user was on**, with **no browser reload** — specified for the fourth time, so the spec requires grepping every error and offline component for `location.reload`, `window.location` assignment and `router.refresh`, listing each with a verdict. The diagnosis is required before the change: which component renders each screen, what triggers the auto-navigation, where the reload originates. **The block also answers the owner's void question in full, because he asked and was confused:** a purchase whose stock has already been sold **cannot be voided** — voiding would remove stock that is no longer there, pushing quantities negative and leaving a completed sale pointing at a batch that no longer exists — so void means "I entered this wrong and nothing has moved yet", and once stock has moved the correction goes **forward** through a purchase return or a stock adjustment, keeping both the mistake and its correction visible.

**PHASE 23 — DATA INTEGRITY (268–274).** The owner supplied the full source for review rather than another screenshot round, and the review found what screenshots could not: **the three most damaging defects were not in the screens where they were reported.** Standing rules unchanged, with one sharpened — capture the evidence before writing the fix.

268. `268-batch-identity-and-stock-integrity` — **the round's reason for existing, and it is urgent enough that the spec orders it deployed before anything else in the group.** Two lines of code account for three separate owner reports. First, `autoBatchNo` (`pharmacy-purchase.ts:70`) builds a batch number **from the date alone** — `AUTO-20260813` — so every auto-numbered receipt on a given day collides; `receiveBatch` then matches a lot on `(branch, medicine, batchNo, expiry)` and, on a match, **adds the quantity and overwrites cost, discounts and retail price**. That overwrite is *correct* for a number a human typed twice and stays; the defect is that a date-only generator makes unrelated deliveries collide, so a second purchase silently re-prices the first and two different expiries collapse into one lot, blinding FEFO. Second, the same collision explains the **false "already sold" void**: `purchaseStockMoved` refuses when any foreign negative movement exists on the lot, so once two purchases share a lot, a sale from the first blocks voiding the second — no change to the void rule is needed, fixing the batch identity fixes it. Third, and independently, `adjustStock` (`pharmacy.service.ts:2187`) calls `applyStockDelta` **always** but `applyBatchDelta` **only when a batch was chosen**, so an adjustment without a batch raises the aggregate and no lot: Inventory reads `stock` and shows 50 while POS allocates from batches and finds 40 — the owner's report, reproduced from the source. The fix makes auto batch numbers unique per tenant per product per receipt behind a database constraint, splits the already-merged lots with movements written and the ambiguous ones **reported rather than guessed**, converges the two quantity sources, and — the durable half — adds a test asserting **`stock.qty == Σ batch.qty`** after a purchase, sale, return, void, adjustment with and without a batch, and an import.
269. `269-import-performance` — the opening-stock receive runs **four sequential awaits per product**, each `receiveBatch` opening its own transaction, which for the first tenant's stated 50,000-product catalogue is **200,000 sequential round-trips** — the single thing standing between that tenant and their stock. Batched into chunked set-based writes with one transaction per chunk, behaviour frozen and every resulting figure required to be identical to the old path's. It also requires auditing the roughly 22 await-in-loop sites in the pharmacy service and fixing **only** those that can exceed ~500 iterations, since rewriting a loop over five cart lines adds risk for no gain. Closed by a measurement rather than a claim: before/after wall-clock, query count and peak memory for a real 50,000-row import, recorded.
270. `270-void-payment-reversal-and-names` — spec 261 told the user to "reverse the payment first, then void" and **no way to reverse a payment existed**; the precondition was specified without the action that satisfies it. The owner's decision closes it: **void auto-reverses the payment, with confirmation**, the dialog naming the invoice, the value, the payment amount and the quantities before anything moves, all in one transaction. A reversal is a **reversing entry, never a deletion** — money that was recorded is never erased — and the same reversal is available standalone from the supplier ledger, since a payment recorded in error is an ordinary mistake. The stock precondition is untouched: a purchase whose stock has moved stays unvoidable. Carries a rule stated once for the whole app after raw ids appeared in three separate places — a purchase's "Recorded by", a void message's payment reference and the ledger's payment rows: **an internal id is never shown to a user**, not in a label, a message, a document or an error.
271. `271-pricing-display-and-pos` — a product added at cost Rs 150 and then purchased at Rs 900 showed only Rs 900, so the figure the owner set had vanished behind the last delivery. Both are true and mean different things — **the product price is what the owner intends, the last purchase is what happened** — so View Item now shows the product figure with the last purchase beneath it in small muted text, or the last cost with a label that says so when no product price is set, applied to cost, sale price, discount and tax alike, with margin **red when negative**. 276. `276-medicine-select-and-purchase-desktop` — a real defect the owner isolated precisely: a product chosen from the **first ~50 loaded options** displays, one found by searching **beyond** that page leaves the field blank while the line still holds the id. **PHASE 24 — THERMAL PRINTING (280–282).** Scoped with the owner around one fact and one honest limit: nearly every thermal printer sold in Pakistan speaks **ESC/POS**, so one renderer covers them all with no per-brand work; and a web app cannot silently reach a USB printer, so wired printers use the browser dialog and a native helper is **parked until a tenant asks**. Split into three deliberately — rendering is pure logic, transport is browser-API work, wiring touches money — so a failure in one stays contained.
280. `280-escpos-rendering` — a pure module: document model in, `Uint8Array` of ESC/POS out, **no browser API, no network, no printer — provable by its imports**. Paper width is a parameter (80mm/48ch, 58mm/32ch) and every layout computes from it; currency renders `Rs` because the `₨` glyph is unreliable on cheap printers, and non-ASCII product names must degrade **without corrupting alignment** — a misaligned total being worse than a missing diacritic. Three documents from spec 131's content contract: the sale receipt (split-batch lines exactly as the cart showed them, grand total double-height, **REPRINT marked** — an unmarked duplicate receipt is a fraud vector), the refund slip, and the Z-report with its variance rendered unmissably. Proven by **golden-byte tests** with a decoder that renders the stream back to readable text, so a changed receipt is a legible diff in review rather than a surprise at a counter.
281. `281-bluetooth-transport-and-settings` — the Web Bluetooth session as a thin state machine (`unsupported · no-printer · connecting · ready · printing · error`), **chunked and paced writes** because BLE characteristic limits are the classic way long receipts truncate on cheap printers, and reconnection on wake. A **Printing** settings group: pair/forget with live state, paper width feeding the renderer, drawer-kick toggle, silent-versus-dialog behaviour, and a **test-print button** — the first thing the owner will press when his printer arrives, so it must tell the truth. The fallback contract is the round's real guarantee: no printer, an unsupported browser, or a mid-print failure all land on the browser dialog with a plain toast, so **every tenant prints from day one** and nothing regresses for one with no Bluetooth printer. Hardware-dependent checks are recorded **awaiting hardware** with the exact steps for the owner — never marked passed unverified (the 148 rule).
282. `282-pos-print-wiring` — one `printDocument` entry point resolving settings → renderer → transport → fallback, every consumer proven by grep to call it, because a per-screen print path is how the next divergence starts. The governing rule is stated first and asserted with a throwing test double: **a printer never blocks money** — a committed sale is never rolled back, re-posted or held by any printing outcome, the cashier is not hostage to paper speed, and a queued offline sale prints **when it commits**, since a receipt for an uncommitted sale would be a lie on paper. The drawer kicks once, on cash only; reprints are marked; refund slips and the Z-report ride the same path. What remains is physical, and 281's awaiting-hardware list is the owner's script for the day the printer arrives.

**PHASE 25 — CLOSING FIXES AND THE KEYBOARD (283–285).**

283. `283-invoice-render-and-inventory-stats` — **the invoice reaches a third attempt**, and the spec stops re-specifying the match. 275 asked for it, 279 asked again with evidence required, and the owner's third PDF still showed a black table header with unreadable text, ellipsised batch numbers and a totals block that was not the mockup's. Three failures of "apply the mockup's declarations" means the built page is very likely **not consuming them at all** — a separate print stylesheet, a `@media print` override, or the document rendering inside a themed container that imposes dark colours. So the deliverable is first a **capture**: which files style the document, the **computed** value of the header, a body cell, the batch cell and the totals block, and **which rule won**. Two content rules are stated as principles rather than fixes — the document is **light only**, because paper is paper and the black header is dark mode leaking in; and **nothing is ever ellipsised**, a long batch number wrapping onto two lines instead, because a document is a record and a truncated batch on a supplier's copy is useless. **Save PDF** reaches its second attempt with the cause named: it calls `window.print()` and relies on the user choosing "Save as PDF", which is Print, not Save — replaced with real generation and a direct download, accepted by **watching the file land with no dialog**. Plus the inventory drawer's four cramped boxes become the owner's redesigned `.istats` family, cost and sale sharing one card.
284. `284-shortcut-engine-and-pos-keys` — the engine is a **per-screen registry** rather than keys bound in components, which is what later lets them be remapped and listed. Its first section is not a key at all but the rule every POS keyboard system gets wrong: **a shortcut must never fire while the user is typing** — a cashier entering a customer's name must not have "D" jump them to discount — which is precisely why the map is built on **F-keys and Alt-combinations**, safe mid-entry by construction. A **barcode scanner is a keyboard**, so a replayed fast scan must fire nothing, proven by test. The POS map adds **F4 direct save** and **F6 direct save with print**, which complete a sale with no confirmation and are therefore guarded: they fire only where the payment dialog itself would pass, commit through the **unchanged** path, and announce themselves with a *"Saved · INV-…"* toast. **Tenant-wide reprint is permission-gated to manager and above** — reprinting another counter's receipt is a fraud vector, while this-device reprint stays open. Row and held-pill navigation are deliberately **fixed rather than remappable**, being conventions rather than preferences. And one owner requirement is generalised into a rule: **every destructive confirmation opens with its confirm button focused**, so Enter completes it however it was opened.
285. `285-shortcut-settings-and-overlay` — **an owner decision reversing a recommendation, recorded as such**: 201 §3 parked customisable bindings and 284's discussion advised skipping them permanently; the owner wants every default remappable, which is his call and is the larger half of this block. Overrides are **per tenant rather than per user**, on the same reasoning that put the PIN gate on roles — a shared counter device must behave identically for whoever is standing at it. Fixed bindings are **shown but not editable, each with its reason**, because a user who cannot find a key needs to know it exists. Conflict detection refuses a duplicate within a scope or against a global while allowing the same key on two different screens, and there is a **printable map** for pinning by the counter. The **`?` overlay shows the tenant's actual keys, never the defaults** — an overlay that lies to whoever remapped is worse than none — and is absent on mobile, where there is no keyboard. The block closes by recording the next group's settled decisions: Returns' three tenant settings (manager approval off by default; a 30-day window that warns rather than blocks; and **expired returns defaulting to Write off**, with Quarantine and Back-to-batch offered and the last carrying a safety warning in the setting itself, since an expired medicine reaching a patient is the risk being accepted), the realtime gap (187's bus exists and was never owner-tested, and the screens do not all subscribe), and push notifications with two honest limits — iOS supports web push only for installed PWAs on 16.4+, and **notification sound is the phone's decision, not the app's**.

291. `291-realtime-stock-and-push` — the owner asked why selling 10 from 50 does not show 40 without a refresh; **184 publishes `stock.updated` and 187 wired POS, but the other surfaces never subscribed**, and none of it has ever been owner-tested — so the spec investigates before building, then subscribes every surface that shows a stock number, coalescing updates so a 50-line import repaints once rather than fifty times. **PHASE 27 — REALTIME ROUND 2, RETURNS FIDELITY AND KEYBOARD ROUND 3 (292–297).**

Every toast, alert, dialog, inline error and empty state in the tenant app is reviewed against three tests: **is it true, is it actionable, is it plain** — and the heading/body mispairing must be fixed **at its mechanism** so the class cannot recur. Recorded as a correctness spec rather than a cosmetic one, because staff act on what they read.
296. `296-new-purchase-as-page` — New Purchase becomes a routed page like the two Returns flows, and the reasoning is worth keeping: purchase entry is a long multi-line task, and a routed page can be linked to, refreshed without loss, and reached by back and forward, none of which a state-flipped panel supports. It gains the abandon warning and, matching what 287 §1 established for held sales, **a draft that survives a refresh** — the same expectation now exists across the app.
297. `297-pdf-badges-and-mobile-warning` — the invoice is close, and two rendering details remain: the PDF **drops border radii and the status dot** that the screen renders, typically because the dot is a pseudo-element the PDF path does not draw, so it becomes a real element and every rounded box is verified **side by side against the screen** — the two being meant to be one document. The mobile over-stock warning **moves above the floating total bar** rather than over it, the owner's decision, with the scroll padding accounting for both. The block closes on the round's real lesson: **a spec that says "make X work" without first establishing why X does not is a guess with a checkpoint on it**, which is what 291 was and what 292 exists to correct.

**PHASE 28 — POS CORRECTNESS, REALTIME COMPLETION AND THE FINAL SHORTCUT MAP (298–300).**

298. `298-stale-allocation-and-stock-guard` — **the round's blocker, and a good example of a symptom that only makes sense once you know the mechanism.** A sale open on desktop for 194 units; the same stock sold on the phone; the desktop warns correctly; the cashier lowers the quantity to what remains — and the commit **still fails**, workable only by deleting the line and adding it again from search. That workaround is the diagnosis: re-adding forces a fresh FEFO allocation, so the line was carrying the allocation it received when it was added, and **lowering the quantity never recomputed it**. The rule is now stated plainly — **an allocation is never older than the quantity it serves** — recomputed on a quantity change, on resume and on load, with the commit-time guard untouched, because the guard was right and the reason it fired was invisible to the cashier. The over-stock warning also stopped surviving a refresh, since the check ran on the realtime event but not on load, so both paths are made to share **one** evaluation function. And the warning moves out of the floating total bar into a `.warnstrip` above it, where it stops competing with the total.
299. `299-realtime-completion` — 292 established the mechanism and POS updates live; this finishes the surfaces that still needed a refresh, with the alerts screen leading because **a stale alerts list is worse than none — it says "nothing needs you" while something does**. Both directions matter: a product crossing into low stock appears live and a restocked one leaves live, with the sidebar count moving in step, since a badge disagreeing with the screen it points at is its own bug. The structural requirement is a single subscription helper proven by grep, because **per-screen socket wiring is exactly why the gap persisted for four rounds** — POS was wired in 187 and every other screen was left to wire itself, which none of them did.
300. `300-pos-shortcut-map-final` — the owner supplied an authoritative list, so this spec supersedes every earlier shortcut spec and **removes anything not in it**. Four decisions applied: page slots move to **`Ctrl+1…9`** because his list had `Alt+5` as both "sale discount" and "jump to slot 5"; `Alt+P` and `Alt+R` are dropped since two routes to one page is clutter and a tenant who wants them assigns a slot; payment methods take **`Shift+1…4`** so plain digits type the amount; and agreeing the prescription warning is **`Ctrl+Enter`** — deliberate, hard to hit by accident, and confirming a legal responsibility. Nine navigation defects land with it, mostly about focus going where the hand expects: arrow keys auto-scrolling a focused row clear of the sticky chrome, Tab from the unit select reaching the **quantity field rather than the `+` button** (steppers are mouse affordances, not tab stops), the unit panel closing when Tab moves on, and the discount block showing a visible focused state as a whole so the cashier can see where they are. **`Alt+N` is made to work inside the payment dialog**, because a walk-in going on udhaar is the one moment a cashier must create an account mid-payment. And an **owner reversal is recorded**: 294 §5 had stopped Tab from activating the customer picker on the principle that Tab moves focus rather than activating — the owner wants the opposite here, because the counter flow is scan → Tab → type the customer, and it is written down so no later spec restores the principle over his decision.

301. `301-keyboard-flow-and-purchase-draft` — flow corrections inside the map 300 fixed, and one of them names a principle the project keeps rediscovering: **a control that exists for the mouse is not a tab stop.** Shift+Tab out of the customer field was landing on the "+" add button rather than returning to Scan/search, which is the same defect as Tab landing on a quantity stepper (300 §2.6) — three separate reports of one idea, so any new control should have its tab behaviour decided rather than discovered. **Enter now walks the line** — unit → quantity → the next line's first field → Proceed to payment when there is no next line — which is what makes a multi-line sale enterable without leaving the keyboard, the point of the whole map. The discount keys `P`, `R` and `0` work from every element in the block **except the value field**, where a keystroke is text rather than a command. And a purchase **draft survives leaving the page**, not merely a refresh as 296 built: restored **silently with a small "Draft restored" note** on the owner's decision, because being asked "continue the purchase you started?" every time is friction while an unexplained pre-filled form is confusing — the note resolves both. Per user, so two people at one tenant never inherit each other's half-entered purchase. **F3 is removed** as an alternative to Alt+C, recorded because 300 listed both by following the owner's own map and he has since decided on one key.

**PHASE 29 — RETURNS COMPLETION AND POLISH (302–303).**

302. `302-returns-flows-and-correctness` — the screens reach their mockups and gain the correctness a refund surface needs. Its central rule distinguishes the two directions for a reason worth stating: **a sale return is capped by what the invoice sold, minus what has already come back — and stock is irrelevant**, because a customer may return what they bought even if the shop now holds none; a **purchase return is capped by that and by the remaining batch**, because you cannot send a distributor goods you no longer have. A **fully returned document still appears in search, marked and unselectable** — hiding it makes staff think they mistyped, showing it tells them the truth. The screen now states **the money consequence before confirming** — *"Refund Rs 1,200 in cash"*, *"Reduces udhaar from Rs 3,000 to Rs 1,800"*, or for a purchase always *"Credit note Rs 4,500"*, since a distributor does not hand money back — alongside the document's age, so the N-day window is visible when it matters rather than only when its warning fires. And a **double-press guard**: spec 108 made returns idempotent on the server, but the button now disables on first press with a spinner, verified by pressing confirm twice rapidly and by a simulated slow response, because the server's idempotency key should be the backstop rather than the first line of defence. Drafts, 50-at-a-time search paging, and a link from a returned document to its return complete it; mobile loses its scan button, gains a step bar that stays visible, and has its two buttons put in **desktop order**, since a control in a different place on each surface is how a hurried user picks the wrong one.
303. `303-keyboard-flow-and-skeletons` — two second attempts and one new capability. The **Enter ring** is restated as a table rather than prose — row → unit select → quantity → next row → Proceed to payment on the last — because 301 specified it in a sentence and it came back incomplete; the likely shape is named (the unit-select case wired for Tab but not Enter, or the option choice consuming the Enter that should advance) and the reason must be recorded before rebuilding. **Split behaves differently from the other payment methods** because it reveals extra fields, so Tab after `Shift+4` belongs in the first of those rather than the close control. The **mobile discount gap** returns for a second time, so the spec requires the computed spacing **measured before and after** and its source named — a second "remove the gap" without a measurement would simply fail a third time. The new capability is **skeleton loaders app-wide**, with the rule that matters: the skeleton **matches the shape of what is coming**, because a generic grey box that resizes on load is worse than nothing; a fast fetch shows none rather than a flash, and a failed one shows the error state rather than spinning forever.

**PHASE 30 — RETURNS CORRECTNESS ROUND 2, LIST INTERACTION AND NAMES (304–309).**

304. `304-returns-ledger-and-history` — **the round's blocker is a consequence that was never specified, which is a different failure from one specified wrongly.** A partial purchase return moved stock and wrote its return, and the supplier ledger did not move at all: 302 built the caps, the consequence preview and the guard — everything the *screen* does — and no spec ever said the credit note must **post**. So the fix is gated behind four captures: the payload, the rows it wrote, the supplier's balance either side, and whether each screen recomputes a balance or reads a stored one. A credit note **reduces what is owed and never touches a payment record**, on 270's reasoning that a reversal is a reversing entry rather than a deletion, and a one-off reconciliation walks the returns already recorded without it, since leaving staging wrong makes every later figure untestable. The second defect is the more instructive: 302 §8 asked for *"Returned on 18 Aug — RET-0012"*, **singular**, and it shipped showing one return where three existed. The build was correct and the sentence was wrong — a document has many returns — recorded that way because **a spec that names a one-to-one relation gets a one-to-one read.** Around them the returned state reaches every surface: a two-variant badge separated by **fill rather than hue** (gold and Alert stay reserved — a return is ordinary business), a summary line in figures, a negative **Returned** row between grand total and paid, and a returns block whose every row and card opens its return. The mockup's own arithmetic becomes the acceptance test — **Rs 92,297.55** — which the screen either shows or the posting is still broken. Two smaller decisions carry a rule each: the payment pill reads `Unpaid · Partly paid · Paid · Settled · Overdue` and never `Returned`, because **one slot holds one kind of status** — the mockup itself had a document reading `Paid` in a list row and `Returned` in its drawer — with `Settled` added since a fully returned invoice that was never paid would otherwise claim it was; and **Void is disabled the moment a first return exists**, both mockups having left it enabled on a partially returned purchase when the locked rule refuses a void once any stock has moved. Finally the components are built **generically and mounted on Purchase alone**, named for a document so Recent Sales mounts them rather than building a second set — the one time in this build a shared component was created **before** the divergence instead of after the sixth report of it.
305. `305-list-row-open-and-realtime` — the owner asked for the whole row to open its record on Inventory, Suppliers, Purchases and Returns, and the interesting part is what must *not* open it: controls, checkboxes, in-row links to other records, and a press-drag that is selecting text rather than clicking. It is specified as **one shared handler that ignores events inside interactive elements**, explicitly not a `stopPropagation` added to each button as it is found, because the second approach is how the next button someone adds silently breaks the row. Enter opens a focused row and **Space does not** — a table row is not a button and Space is the page's scroll key — and the handler is built so 306 wires the existing action rather than adding a second path to it. The realtime half is subscription, not a new bus: 292 established the mechanism and 299 finished the surfaces then known, and these three were simply never wired, so a purchase return posting its credit note now moves the supplier's owed figure on an open list. Three rules keep it honest — **display only**, a row the user is interacting with updates without moving focus or closing anything, and **sort position is preserved while a list is being read**, since a row that jumps to the top slides out from under a pointer.
306. `306-keyboard-unit-select-and-list-preset` — the POS unit select on its **third attempt**, and this time the owner's second symptom identified the mechanism for us: arrow keys were *also* blurring the control, which means **any option change commits and leaves**, which is why Enter blurred without advancing. The spec separates the two — **changing a value is not choosing it**: ↑/↓ move through options with focus and panel retained and nothing committed, Enter commits and lands on that row's quantity field. Ten repetitions from different starting states, because an intermittent fix that passes once has not been fixed (294). The second half is the owner's own proposal for one shared list-screen preset, accepted with its shape corrected: the preset supplies **navigation** — F2, ↑/↓, Home/End, Enter, an Esc ladder, Alt+N — and each screen **declares its own second action** through 284's registry, because the owner's `Alt+A` meant adjust on Inventory, a payment on Suppliers and a receipt on Purchases, and **one key with three meanings is worse than three keys**. Two rules generalise: **F2 means "focus this screen's primary input"** — the scan field on POS, the search field on a list, so Lab and Clinic inherit it — and **Esc does the nearest undoable thing and then stops**, never navigating away.
307. `307-full-names-and-identity` — the owner asked for complete medicine names in Inventory and the New Purchase select, pointing at POS search as the surface that already does it right. The decision recorded is **wrap to two lines, never truncate, with a tooltip explicitly rejected**: a tooltip is a mouse affordance that does not exist on a phone, and the tail a truncation removes — *500mg (Tablet)* — is exactly what distinguishes two products that share every earlier character. The secondary line still truncates, because that is context while the name is identity, and where a fixed column and a two-line name conflict **the column yields and the money columns never do**. Added from the owner's screenshots rather than his report: `owner@ganatra-clinic.mp` was rendering where a person's name belongs, in a sale's identity line and under **Counter** — the same class of defect, since **an email address is a credential** and standing rule 7's spirit covers it as squarely as a database id.
308. `308-returns-desktop-to-mockup` — **the third attempt at these two screens, and the previous wording is recorded as the reason.** 293 built the frame; 302 §5 said *"spacing and gaps throughout"* and *"heading and description exactly as the mockup states them"*, and every one of those items came back on the owner's next test. The lesson is stated plainly — **a phrase that hands the agent a judgement call gets a judgement** — so the headings and descriptions go in as **literal quoted strings** and each gap gets its own line with a mockup value, a deployed value, a named source and an after value. The spec also names the likely single cause: five gaps reported as five bugs are usually block spacing hand-set per element instead of taken from the shared layout, and if the audit shows that, the five resolve together. Two items arrived from the screenshots — the search list not scrolling its highlighted option into view, so a user chooses blind, and a reason select rendering three of its five options as `Custo…`, `Wrong…`, `Dama…` while 302 had already asked for that column to be widened.
309. `309-returns-mobile-and-copy` — the phone equivalents and the block's close. The bottom space is a **second report** and gets 303 §2's treatment — measured before and after with its source named — with one candidate worth stating in advance: if the cause is a **second `--mchrome` reservation stacking on the one 302 added**, that is a different defect from the one 302 believed it was fixing. The whole line card now ticks its checkbox, reusing 305's handler so a tap inside the quantity field or reason select still does its own job. And the owner asked what an information box at the end of the flow was for, which is its own answer: it was 302's return-window explainer, detached from anything it explained, and it becomes **one quiet line beneath the search field naming the window in days** — a rule with its number is worth reading and a rule without one is not.

> **STANDING LESSON FROM PHASE 30, and the more expensive of the two:** **a consequence that is never specified is never built.** 302 specified everything the returns *screen* does and nothing about what its credit note does to the ledger, so the screen was reviewed and the money was not — because nothing asked anyone to look. **When a spec changes money, its acceptance belongs on the balance that results, not on the screen that caused it.**

**PHASE 31 — LEDGER TRUTH, PAYMENTS AND PERSONALIZATION (310–316).**

310. `310-ledger-truth` — the round opened with the owner's own arithmetic: the ledger's closing row showed Rs 533,382.42 credit against Rs 531,299.32 debit — the supplier holds Rs 2,083.10 of the tenant's money — while the header read **"Running balance Rs 0 · All invoices settled"** and the purchase screen read −2,083.10. The column was right; the header **clamped a negative at zero**, because when 304's credit notes created a state no screen expected — a supplier advance — nobody audited the surfaces that render balances. So the fix is a label, not a computation: **`Advance with supplier Rs X`**, everywhere a balance renders, plus newest-first sorting, a pagination count that was reading "1 of 31" on page 4, and an export toast announcing "Catalogue exported" for suppliers. The document-shows-one-return defect reached its **third attempt** with the cause finally visible: 304 fixed the purchase *view* while the owner's screenshot was the return flow's *Step 1 card* — a different surface reading the old way, which is the shared-component rule failing in the other direction. And a human-gated verify-only query checks whether the Rs 2,083.10 is real or a doubled entry — the agent reports, never deletes.
311. `311-names-and-identity` — **307's misdiagnosis corrected on the record.** The incomplete Inventory name was never truncation — the same build showed `Actifed` on Inventory and `Actifed 60ml (Syrup)` on Returns, so two surfaces were composing names two different ways. One composer now: primary name + strength, secondary generic · form · pack, per the new mockup's `.medcell`. The owner's "repeated strength" confusion — `60ml · Syrup · 60ml` — turned out to be catalogue data, a bottle volume typed into the strength field, met three ways: the composer prints a value once when strength equals pack, the item form warns (never blocks) on a liquid or cream strength with no `/` or `%`, and a one-off report lists the bad rows for the owner to correct by hand — the agent never edits catalogue data. The email-as-person defect from 307 §2 proved to be a class, not two instances, and closes app-wide as one identity component: **display name + role chip, never a login** — with signed, coloured stock-movement quantities and each movement crediting its user.
312. `312-realtime-and-interaction` — 305 wired these lists to the bus and the owner's report exposed what the acceptance missed: **updates arrived, inserts never did** — a created purchase appeared nowhere without a refresh, the likely shape being a subscription filtered to ids already on screen. Captured with two sessions before fixing, then audited across every screen the pattern was mounted on. Around it, three interaction defects with one lesson each: the purchase Print dialogue had grown its own overlay (one modal shell, grep-proven); closing Print then View Purchase landed on *Suppliers* because a sheet pushed a route it never popped (capture the history stack first); and a pressed filter pill did nothing while its fetch ran — every press now paints instantly with 303's skeleton, Adjust stock opens instantly the same way, and the desktop card grid mounts 305's row handler rather than growing a second one.
313. `313-payments-and-permissions` — payment tracking arrives sized to what a counter can bear: Settings lists the tenant's real **payment accounts** (Cash built-in, deactivate never delete), and every non-cash payment records **which account the money landed in (required) plus a reference (optional, editable later)** — the owner's call, since a forced reference field teaches cashiers to type "123". Day-close isn't built; the data now exists so it can report per-account totals when it is. Three permissions, each enforced frontend and backend: **change sale date**, **print without sale** (renders documents, commits nothing), and **void sale** — which lives on Recent Sales because POS sells and Recent Sales manages, reverses by entries never deletions, restores consumed udhaar, and is server-refused once any return exists. The locked purchase rule — void or correct forward, never edit — now covers sales symmetrically.
314. `314-supplier-ledger` — the Accounting block's central decision — **one ledger, Simple and Pro views** — arrives early on one screen: a switcher renders the same rows as Debit/Credit for the trained eye or as one signed, coloured column for everyone else, and switching re-renders without re-fetching. A **Returns tab** joins Ledger · Purchases · Payments carrying credit-note numbers in 304's settlement slot. The rows stop hiding things: reference and description never ellipse (the reader is there for the detail), the missing reverse button is found and its absence explained, and the Recent blocks go — newest-first made them redundant. **Refund received** lets a supplier hand an advance back, capped at the advance, through 313's account and reference. And the mobile stacking defect — Record Payment opening *behind* the ledger sheet — is fixed in the shared sheet component with an app-wide audit, not on the screen it was reported.
315. `315-inventory-and-purchase-view` — the owner redesigned the Purchase surfaces around 304's returned-state work, and the spec's one structural sentence is that **304's components are mounted, never rebuilt or restyled**. The new filter pills (`Partially returned`, `Fully returned`) join the payment pills; every moved block gets 308's measured-line treatment because "match the mockup" as one bullet is the wording that already failed twice. Add/Edit item gains the mockup's **live margin badge** — markup on cost, (sale − cost) / cost, the reading retail pharmacy quotes and the only one exceeding 100% — display only, the guard still warns and never blocks. And `Tenant default` alone stops being an answer: every inherited value reads **`17% (Tenant default)`** — the resolved value with its source muted — through one formatter, while the resolution orders themselves stay locked and untouched.
316. `316-personalization-and-language` — preferences become **per-user, per-screen, with the control as the setting**: card/list (defaulting card-mobile, list-desktop) and 314's Simple/Pro ride one preference store that survives login and device; no settings page, the app remembers the last choice. Profile gains Full-name editing — the display name 311 renders everywhere — with roles staying assigned, not chosen. The language decisions lock after honest pushback both ways: **Outstanding → Baqaya** on every balance-owed label, **Credit limit → Udhaar limit** (it caps udhaar; same word, correct), while **Credit note stays** — it is a document name and trade language, and "Udhaar note" would say the opposite of what the document is. Display strings only; columns and identifiers never rename. Return reasons split into two tenant-editable lists — a purchase return and a sale return are different events, and "Customer changed mind" on a purchase was the proof — seeded with placeholder defaults precisely so Ganatra's trade wording can replace them without a spec.

> **STANDING LESSON FROM PHASE 31:** **when a rule creates a new state, audit every surface that renders the old states.** 304's credit notes made a supplier advance possible; the ledger header, written when a payable could only be zero or positive, clamped the new state out of existence — the truth was computed and then hidden. The companion from 310 §2: fixing a defect on the surface it was found leaves it alive on every other surface reading the same way — the shared-component rule cuts in both directions.

**PHASE 32 — ALLOCATION, PAYMENTS ROUND 2, AND SCREENS TO MOCKUP (317–322).**

Allocation now sits **on top of** the frozen posting: a credit note relieves **its own invoice's remainder, then the oldest open invoice, then becomes advance** — rows, never edits, with the supplier's total baqaya provably identical before and after, since allocation moves money *between* invoices and never in or out. > **STANDING LESSON FROM PHASE 32:** **a rule is specified against the list of every surface it governs, and a fix is scoped to the class, not the reported instance.** 313's account tracking missed Split and New Purchase because the spec named the surfaces that prompted it; 311's icon fix missed the card views because it fixed where the owner pointed. The shared-component rule binds rules and fixes alike — both directions, every time.

> **STANDING LESSON, recorded because it will recur:** when a value does not appear on screen, **capture the evidence before writing a spec** — the API response first, and **the database row when the payload looks correct**. `test:unit` never touches a real database and the fakes supply fields the real path may not, so a green suite proves nothing about what a screen renders. Five rounds were spent tracing an intact backend because nobody looked at the payload; a sixth was avoided by one query that showed every sale had `customer_id = NULL`.
